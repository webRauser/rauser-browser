## 2026-11-24 — Stash design review and product roadmap

**Recommendation.** Make Stash a fast queue for revisiting web pages and work artifacts. The next release should let people find an item, see what Brauser actually read, take the next action, and return to the same place in the queue. Follow that with a personal shortlist and search across the local summaries and notes Brauser already owns.

Stash's advantage is that a page can share an identity with its Brauser summary and notes. A person can save a work ticket, document, or public article once, then decide whether to read the original or rely on saved context. The summary's coverage matters as much as its availability when that decision is about a work artifact.

### What exists today

- The sidebar saves the current HTTP(S) page to a user-selected home. The host deduplicates by record key, keeps the first saved title and time, and reuses an owned summary or hands off to the ordinary summary workflow. A save without a harness can still appear in Stash. [Design §5.4](../../DESIGN.md#54-stash), [sidebar save flow](../../extension/panel.ts#L1672)
- Stash opens as a dedicated tab. It shows To read, Done and All, matches a case-insensitive substring against title or saved URL, and shows newest saves first in pages of 20. The preview can open the original in a new tab or the owned summary through the native opener. The tab refreshes on return and offers a manual Refresh. [Stash UI](../../extension/stash.ts#L119), [host list](../../host/src/stash.rs#L329)
- Mark done writes a receipt bound to the original entry bytes. The entry and its summary stay available through Done and All. The native API currently supports save, list and complete. The management directory on the reviewed main already links to Stash and surfaces an unread count that may show 20+. [Completion contract](../../host/src/stash.rs#L308), [management directory](2026-11-24-sidebar-management-directory.md), [exact-count proposal](../improvement-feed/2026-11-24-show-exact-stash-unread-total.md)

### Where the experience breaks down

| Finding | Effect | Recommended design |
| --- | --- | --- |
| Most of the chrome frames a single status dropdown, two repeated titles, timestamps down to seconds and identical chips in the list and preview. | The screenshot asks the eye to scan three panels for one item's main action. At smaller widths the filter panel still takes a full row. | Use a compact bar with To read, Done and All beside search. Keep a two-pane list and detail layout at wider widths, with one quiet divider. In the list show title, source, short save date and an exception such as Limited summary. Keep supplemental metadata in the detail. [Layout markup](../../extension/stash.html#L19), [row metadata](../../extension/stash.ts#L90) |
| Selecting a row updates the preview and leaves focus on the row. At stacked widths, the preview can be below the viewport, and the jump button follows the result list. | With 20 results and more available, reaching the preview jump or first source action took 20 Tab presses from row 2. The preview heading sat below an 800 px viewport at both 320 and 640 px widths. | On narrow widths, activate a result to open a focused detail view with Back to results. On desktop, put a keyboard path to the selected detail next to the active row or move focus on explicit activation. Provide a direct return to the invoking row. [Selection](../../extension/stash.ts#L119), [jump control](../../extension/stash.html#L56), [stacked layout](../../extension/explorer.css#L621) |
| Returning to Stash reloads the first batch even when a later batch is selected. | In a 23-item fixture, returning with item 21 selected kept the query, dropped the last three rows, and switched the preview to item 1. Anyone checking multiple source tabs can lose their place. | Reconcile refreshed data with the selected item and loaded range. Retain query, status view, selection and scroll position on return. If a selection truly leaves the view, explain it and focus the nearest remaining item. [Replacement of results](../../extension/stash.ts#L166), [refresh and visibility](../../extension/stash.ts#L236) |
| A saved summary can describe a wrapper without the underlying content. The screenshot conveys that limitation in prose. Stash's summary response includes classification and overview, while Artifact Explorer also exposes reading coverage. | A reader can see that a summary exists and still miss that it only covers the visible page or part of the artifact. An entry with no summary sends the reader through the source tab and sidebar to retry. | Show coverage next to the overview and make Open original prominent for limited, missing or unknown coverage. Reuse Brauser's existing coverage vocabulary and offer a checked handoff to the existing summary workflow. [Stash summary fields](../../protocol/schema.json#L884), [owned coverage parser](../../host/src/summary.rs#L250), [Explorer coverage](../../extension/explorer.ts#L215), [retry proposal](../improvement-feed/2026-11-23-resume-stash-summaries-from-saved-pages.md) |
| Mark done is one-way through Stash. Re-saving an already-completed record returns the existing entry. The host also checks for a summary-file conflict before publishing a new entry. | An accidental completion takes the item out of To read with no in-app recovery. A conflict in one artifact can prevent the separate act of saving its link. | Add Undo and Move to To read after the queue layout. Make link-save success independent of summary outcome where doing so preserves ownership rules, and keep any summary conflict visible with its repair action. [Save and completion behavior](../../host/src/stash.rs#L257), [Mark done UI](../../extension/stash.ts#L282) |

The current status messaging correctly distinguishes an in-flight search from a settled empty result. The delayed-search probe showed “Loading saved pages…” with the empty state hidden. Keep that behavior while making loading, empty queue, no matches, setup and host errors easy to recognize. The five existing Stash headless tests also cover safe source navigation, stale replies, paging, revision checks and axe at 1200 px light and 320 px dark. Axe coverage and the keyboard observations measure different aspects of the experience. | wallabag | Its parser extracts readable article content, moves read items to Archive, and offers article annotations and export. These comparisons use product documentation, so they establish advertised workflows. The priorities below are a judgment about Brauser's fit, based on the code, screenshot and synthetic browser checks.

### What to build next

| Order | Scope | Acceptance |
| --- | --- | --- |
| **1A. Make browsing reliable** | Compact two-pane desktop layout, focused detail and Back on narrow layouts, visible status controls, and one direct keyboard path each way. Keep the existing Open original, Open summary, Mark done, Settings, Refresh and paging reachable. Keep Refresh secondary and preserve the current status names. | At 320, 640, 900 and 1200 CSS px, search, open result, reach its first action and return using the keyboard in no more than two navigation steps each way from the row or detail heading. With at least 23 items, returning from a source or a successful refresh keeps a later-page selection and its scroll position. Check mobile reflow, zoom, long titles, both themes and delayed/failed replies. |
| **1B. Explain what is available** | Put coverage on an inline saved-summary preview. Show no summary, unknown legacy coverage, page only, partial, or whole artifact, based on owned metadata. Add in-place retry handoff to the loaded source and distinguish save, running, and summary outcomes when those states are known. | A wrapper-only summary and an older summary with unknown coverage are visibly distinguishable without reading the overview. A failed or unavailable summary leaves the saved link usable. Retry uses the existing capture and summary flow on the right loaded tab. An unowned summary path stays untouched and receives actionable feedback. |
| **2. Make the queue forgiving** | Add Undo after Mark done, Move to To read from Done, and next-item focus after completion. Add Pin for items the user chooses to prioritize. Offer newest/oldest sort once needed alongside a pinned view or pinned-first ordering. | Undo and requeue survive reload, restart and reindex. Legacy completion receipts read the same. Repeated clicks and conflicting views preserve a consistent result. Pin is independent of AI importance and does not alter the original save time. |
| **3. Find saved work by context** | Extend search to owned summary overviews and then saved notes, reusing the same record keys and existing note/Explorer pathways. Show matched text and source/type/coverage filters. Include Done in a deliberate All view. Benchmark before deciding whether a rebuildable index is necessary. Evaluate explicit Markdown/link-list export once a concrete transfer workflow is identified. | Find a phrase that appears only in a summary or note, recognize why it matched, and retrieve it from page 2 or later. Apply filters before pagination and bound work. Verify on 20, 200 and 2,000 mixed fixtures. Establish and record local first-page and incremental-search performance targets from those baselines. |

For 1A, the desktop wireframe is a narrow header, a single row of status controls and a split between the queue and the selected item. The primary content at right is title, source, coverage, saved overview and actions. The narrow layout shows either the queue or selected item. State changes retain the durable entry and summaries. The first change can use the current list contract. Treat the coverage projection and summary retry as a separate host/extension follow-up so each piece can be validated on its own.

Completion recovery changes the storage contract. Evaluate a version-bound additive state record or transition receipts that keep the original save and completion evidence readable. Specify retries, concurrent writes, conflict handling, restart and downgrade before implementing a requeue control. Retain host-derived keys, selected-home authority, symlink checks, safe source navigation and inert summary rendering. If a summary projection changes the strict wire response, validate coordinated host/extension compatibility and legacy records. [Safety invariants](../agents/safety.md), [filesystem contract](../../DESIGN.md#44-filesystem-rules)

**Hold for evidence.** Defer offline snapshots, reading position, full-page highlights, bulk refinement, reminders, and import until there are identifiable repeated workflows the queue cannot serve. A public-article snapshot pilot would need explicit save and removal, visible capture coverage and size bounds. Authenticated work pages stay on the existing source-and-summary path during such a pilot. Feed ingestion, audio, sync and a second note editor add separate product surfaces and have a lower priority for this audience.

### How to tell whether the next release worked

Run a short comparative exercise with a small mixed queue, then a multi-page synthetic queue. Ask readers to save and retrieve a work artifact, handle a partial summary, and complete an item after visiting its source. Record steps, time to reach the correct action, lost selection, mistaken reads of coverage and requests for a full copy of the original. Compare the current and revised builds with the same tasks. Use the local fixture and opt-in feedback in keeping with Brauser's no-telemetry design.

The baseline is the main branch at `961cdbc4` on 2026-11-24 and the supplied screenshot. Headless Chromium used the built Stash page with synthetic native replies, at 320, 640, 900 and 1200 px. The screenshot informed the visual audit. The tests did not access a real saved page, selected home, native opener or summary harness. No adoption, retention or workload data was available, and the competitor review did not require accounts.

**First implementation slice.** Make an activated result open its detail within two keyboard steps, then return focus and scroll to the same result even on a later page. Put that acceptance journey in the Stash headless suite before widening the feature scope.
